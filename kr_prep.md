# Подготовка к контрольной работе №4: Комплексный разбор концепций

## 1. «Когда я выберу rebase, а когда merge? Почему?»

### Выбор Rebase (перебазирование):
- **Сценарии:**
  1. Локальная разработка фичи перед отправкой на Code Review: приведение локальной цепочки черновых коммитов к чистому виду (`git rebase -i`).
  2. Актуализация персональной ветки изменениями из `main` (`git pull --rebase origin main`).
- **Почему:**
  Rebase позволяет избежать засорения истории избыточными техническими коммитами слияния вида `Merge branch 'main' into feature`. В результате история проекта остается строго линейной, удобной для чтения через `git log`, простого бинарного поиска багов (`git bisect`) и чистого отката.

### Выбор Merge (слияние):
- **Сценарии:**
  1. Релизные этапы и слияние проверенных фичей в `main` (через Pull Request или явный 3-way merge с сохранением истории).
  2. Интеграция параллельной работы нескольких крупных команд или веток долгоживущих версий (`release-1.x`).
- **Почему:**
  Merge сохраняет реальный хронологический контекст и факт параллельной разработки. Создается трехсторонний коммит слияния, не переписывающий историю и исходные хэши коммитов.

## 2. «Что произойдёт, если я сделаю rebase публичной ветки, с которой работают коллеги?»

### Последствия нарушения «Золотого правила Rebase»:
1. **Переписывание истории и рассинхронизация хэшей:**
   Rebase не просто переносит коммиты, он пересоздает их заново с новыми SHA-1/SHA-256 хэшами. Для Git старые и новые коммиты — это совершенно разные объекты.
2. **Конфликт истории на машинах коллег:**
   Если разработчик запушит перебазированную ветку с флагом `--force`, удаленный репозиторий примет новую историю, но у всех коллег локально останется старая ветка.
3. **Дублирование коммитов при pull:**
   При последующей попытке коллег выполнить `git pull` Git попытается объединить ветки с общим предком через слияние, что приведет к дублированию всех коммитов (оригинальных и перебазированных), каскаду сложных merge-конфликтов и загрязнению репозитория.

## 3. «Зачем нужен multi-remote и в каких реальных сценариях он применяется?»

### Назначение Multi-Remote:
Multi-remote — это привязка локального Git-репозитория одновременно к двум или более удаленным серверам (remotes).

### Реальные производственные сценарии:
1. **Отказоустойчивость и георезервирование (Backup / Disaster Recovery):**
   Основная разработка ведется на GitHub, а зеркальная копия (Mirror) непрерывно синхронизируется на корпоративный GitLab или локальный On-Premises сервер компании на случай сбоев облачного провайдера или сетевых ограничений.
2. **Open-Source контрибуция (Forking Workflow):**
   Разработчик имеет `origin` (свой личный форк на GitHub, куда пушит свои ветки) и `upstream` (оригинальный репозиторий проекта, откуда непрерывно подтягивает свежие изменения мейнтейнеров).
3. **Гибридный пайплайн (CI/CD разделение):**
   Код пушится на GitHub для открытого взаимодействия, а закрытые внутренние тесты безопасности, сканирование уязвимостей и деплой на защищенную инфраструктуру запускаются через зеркало в закрытом корпоративном GitLab CI.
