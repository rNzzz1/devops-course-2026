## 3. Теоретическая справка

### 3.1. Merge vs Rebase: фундаментальные отличия

Обе команды решают общую задачу — интеграцию изменений из одной ветки в другую, но делают это принципиально разными способами:

1. **Merge (Слияние):**
   Создает новый трехсторонний коммит слияния (*3-way merge commit*), объединяющий две истории. История остается нелинейной: в логе явно виден параллельный характер разработки.
   - *Плюсы:* абсолютная безопасность, не переписывает существующие коммиты и историю.
   - *Минусы:* засорение истории избыточными merge-коммитами («железная дорога»).

2. **Rebase (Перебазирование):**
   «Пересаживает» коммиты текущей ветки на верхушку целевой ветки. История становится строго линейной, будто разработка велась последовательно.
   - *Плюсы:* чистая, аккуратная история, удобная для чтения логов и бинарного поиска багов (`git bisect`).
   - *Минусы:* переписывает историю (изменяет SHA-хэши).
   - *Золотое правило Rebase:* **Never rebase public branches** — никогда не применять к публичным разделяемым веткам.

### 3.2. Возможности Interactive Rebase (`git rebase -i`)
Инструмент интерактивного редактирования истории позволяет:
- `pick`: сохранить коммит без изменений;
- `reword`: отредактировать сообщение коммита;
- `edit`: остановиться для изменения файлов или разделения коммита;
- `squash`: слить коммит с предыдущим и объединить их сообщения;
- `fixup`: слить коммит с предыдущим, отбросив сообщение текущего;
- `drop`: полностью удалить коммит.

### 3.3. Архитектура Multi-Remote
Git позволяет привязать к одному локальному репозиторию несколько удаленных хранилищ (`git remote add <name> <url>`), а также настроить множественные адреса отправки для одного remote (`git remote set-url --add --push origin <url>`). Это решает задачи:
- Резервного копирования и георезервирования (GitHub + зеркало на GitLab / On-Premises);
- Контрибуции в Open-Source (Forking Workflow: собственный `origin` и официальный `upstream`).

### 3.4. «Машина времени» Git
- **Cherry-pick:** Точечный перенос выбранного коммита по его SHA-хэшу в текущую ветку.
- **Reflog:** Локальный журнал всех перемещений указателя `HEAD`, позволяющий найти и восстановить случайно удаленные коммиты и ветки.
- **Revert:** Создание нового коммита, вносящего строго противоположные изменения, что позволяет безопасно откатить дефект в публичной ветке `main`.

### 4.2. Задание 2. Rebase vs Merge — сравнение на практике

Проведено сравнительное моделирование слияния ветки `demo/merge-example` двумя стратегиями.

#### 1. Вариант через классический Merge:
```text
*   3ec8c4d (HEAD -> main) merge: integrate feature A
|\  
| * 859bade (demo/merge-example) docs: add details for feature A
| * 96cb729 feat: add feature A description
|/  
*   8e4d97a merge: resolve conflict in README.md
```
*Пояснение:* В истории видна характерная «галочка» — две параллельные линии слиты коммитом `3ec8c4d`. История нелинейна.

#### 2. Вариант через Rebase + Fast-Forward:
После отката `main` через `git reset --hard HEAD~1` выполнен `git rebase main` и слияние `git merge demo/merge-example`:
```text
* 859bade (HEAD -> main) docs: add details for feature A
* 96cb729 feat: add feature A description
* 8e4d97a merge: resolve conflict in README.md
* e90c164 docs: add practice 2 report in markdown and docx formats
```
*Пояснение:* История стала строго линейной, без ветвлений и без создания дополнительного merge-коммита.

### 4.6. Бонусное задание. Настройка Git Hook (`commit-msg`)

В репозитории настроен исполняемый хук `.git/hooks/commit-msg`, проверяющий формат сообщений:
```bash
#!/bin/bash
commit_msg=$(cat "$1")
pattern="^(feat|fix|docs|chore|refactor|merge|test|ci|build|perf|style)(\(.+\))?: .+"

if ! echo "$commit_msg" | grep -qE "$pattern"; then
  echo "❌ ОШИБКА: Сообщение коммита не соответствует Conventional Commits."
  echo "   Ожидаемый формат: <type>: <description>"
  exit 1
fi
```
- Попытка коммита `bad message` заблокирована.
- Коммит `chore: test git hook` успешно прошел проверку.

## 6. Ответы на контрольные вопросы (для самопроверки)

### 1. В чём принципиальная разница между `merge` и `rebase`? Когда что использовать?
**Ответ:**  
`Merge` соединяет ветки созданием специального коммита слияния (3-way merge commit), сохраняя историю нелинейной. `Rebase` переносит базу коммитов на вершину целевой ветки, выстраивая строго линейную историю. `Rebase` применяется для очистки локальных фича-веток перед отправкой в Pull Request; `merge` — для слияния готовых релизных веток в `main`.

### 2. Почему нельзя делать rebase публичных веток? Что произойдёт, если нарушить это правило?
**Ответ:**  
Rebase пересоздает коммиты с новыми SHA-хэшами. Принудительный push (`--force`) перебазированной публичной ветки рассинхронизирует репозитории коллег. При следующем `git pull` у них произойдет дублирование коммитов и возникнет множество тяжелых конфликтов.

### 3. Что делает команда `git rebase -i HEAD~5`? Перечислите доступные действия.
**Ответ:**  
Запускает интерактивный режим перебазирования последних 5 коммитов. Доступные действия: `pick` (оставить), `reword` (изменить текст коммита), `edit` (остановиться для правки кода), `squash` (слить с предыдущим коммитом и склеить сообщения), `fixup` (слить с предыдущим, отбросив сообщение), `drop` (удалить коммит).

### 4. Чем `squash` отличается от `fixup` при interactive rebase?
**Ответ:**  
Оба действия склеивают коммит с предшествующим ему. Однако `squash` открывает текстовый редактор для редактирования объединенного сообщения обоих коммитов, а `fixup` отбрасывает сообщение текущего коммита, сохраняя сообщение предыдущего.

### 5. Что такое `cherry-pick` и в каком сценарии он полезен?
**Ответ:**  
`cherry-pick` — команда точечного применения конкретного коммита из одной ветки в другую по его хэшу. Полезна в сценариях Hotfix, когда критический баг исправлен в развивающейся экспериментальной ветке и его нужно немедленно перенести в `main`, не сливая всю ветку целиком.

### 6. Как восстановить коммит, который был «потерян» после `git reset --hard` или удаления ветки?
**Ответ:**  
С помощью локального журнала `git reflog`, хранящего историю всех перемещений указателя `HEAD`. Найдя в reflog хэш утерянного коммита, ветка восстанавливается командой `git checkout -b <branch_name> <hash>`.

### 7. Чем `git revert` отличается от `git reset --hard`? Почему для публичных веток нужно использовать именно `revert`?
**Ответ:**  
`git reset --hard` переписывает историю, удаляя коммиты из графа (что разрушает синхронизацию у коллег). `git revert` создает новый коммит, применяющий обратные изменения, сохраняя историю линейной и безопасной для совместной работы в публичных ветках.

### 8. Как добавить второй remote и настроить push в оба репозитория одной командой?
**Ответ:**  
Добавить второй remote: `git remote add mirror <url>`. Затем добавить второй push-URL к origin: `git remote set-url --add --push origin <url_зеркала>`. После этого `git push origin main` будет одновременно отправлять коммиты в оба репозитория.

### 9. Что такое Git hooks? Приведите пример полезного pre-commit hook.
**Ответ:**  
Git hooks — клиентские скрипты, автоматически вызываемые Git при определенных событиях. Пример полезного `pre-commit` хука: запуск статических анализаторов (линтеров) и unit-тестов перед фиксацией коммита с блокировкой коммита при наличии синтаксических ошибок или непройденных тестов.

### 10. Опишите Forking Workflow. Чем он отличается от GitHub Flow?
**Ответ:**  
В GitHub Flow все члены команды работают с общим центральным репозиторием и создают ветки прямо в нем. В Forking Workflow каждый контрибьютор создает на сервере личную копию (Fork), пушит изменения только в свой репозиторий, а в базовый репозиторий изменения предлагаются через межрепозиторный Pull Request. Это стандарт разработки ядра Linux и открытых Open-Source проектов.
