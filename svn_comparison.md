# Анализ и сравнительное исследование: Git vs Subversion (SVN)

## Вопрос 1. Почему в Git ветвление «дешёвое», а в SVN — «дорогое»?

### Механика ветвления в Git
В Git ветка не является копией файлов или каталогов. Ветка — это легковесный 41-байтный указатель (текстовый файл в директории `.git/refs/heads/<branch_name>`), хранящий 40-символьный SHA-1/SHA-256 хеш коммита.
- **Создание ветки в Git:** Создание нового указателя на существующий объект коммита (`HEAD`). Операция выполняется за константное время $O(1)$ и занимает доли миллисекунды независимо от размера репозитория (будь то 10 файлов или 100 000 файлов).
- **Слияние (Merge) в Git:** Git сохраняет направленный ациклический граф коммитов (DAG). При слиянии Git автоматически находит ближайшего общего предка (*merge base*) с помощью трехстороннего слияния (*3-way merge*), минимизируя конфликты и отслеживая перемещения файлов.

### Механика ветвления в SVN
В SVN (Subversion) архитектурно отсутствует понятие «легковесной ветки». Ветка в SVN создается как операция копирования директории внутри файловой структуры репозитория на сервере:
`svn copy https://svn.example.com/repo/trunk https://svn.example.com/repo/branches/feature-x`
- Хотя сервер SVN оптимизирует это на уровне файловой системы метаданных («дешевая копия» / *copy-on-write* в базе FSFS), логически это полноценная папка.
- Переключение между ветками (`svn switch`) требует обращения к центральному серверу по сети, проверки разницы и перезагрузки рабочего дерева.
- До версии 1.5 в SVN не было отслеживания слияний (*merge tracking*) вовсе, а в современных версиях слияние веток остается громоздкой операцией, требующей ручного учета ревизий и приводящей к так называемому «tree conflict» (конфликтам дерева каталогов).
- В результате ветвление в SVN организационно воспринимается как «дорогое»: команды в SVN стараются минимизировать создание веток и работают в едином `trunk`, что провоцирует нестабильность кода.

## Вопрос 2. Можно ли в SVN сделать коммит без интернета? Почему?

### Ответ: Нет, в SVN сделать коммит без доступа к сети невозможно.

### Причина:
- **Централизованная архитектура SVN:**
  В SVN существует ровно **одно** истинное хранилище данных — центральный сервер репозитория. Локально у разработчика находится лишь так называемая *Working Copy* (рабочая копия текущей ревизии файлов с служебными скрытыми файлами `.svn`).
- **Отсутствие локальной базы коммитов:**
  В рабочей копии SVN нет локальной базы истории или механизма очередей коммитов. Команда `svn commit` отправляет дельты файлов по протоколам HTTP(S) или SVN непосредственно на центральный сервер, где инкрементируется глобальный номер ревизии хранилища ($r_{N+1}$). Если сетевое соединение отсутствует или сервер недоступен, операция `svn commit` немедленно завершается с ошибкой сети.
- **Контраст с Git:**
  Git является **распределенной** (децентрализованной) VCS. Локальная папка `.git` содержит полноценный независимый репозиторий со всей историей, графом коммитов, объектами blob/tree и ветками. Разработчик в Git может днями работать в офлайне (в самолете, поезде, при сбоях провайдера), создавать десятки коммитов, переключать ветки, делать rebase и cherry-pick, а при появлении сети выполнить `git push` на удаленный сервер.

## Вопрос 3. В каких сценариях SVN до сих пор может быть предпочтительнее Git?

Несмотря на доминирование Git (более 95% проектов), SVN сохраняет свою нишу в специфических корпоративных и индустриальных задачах:

1. **Монолитные репозитории с огромными бинарными файлами (GameDev, 3D-модели, CAD):**
   - В индустрии разработки игр (Game Development), анимации и промышленном дизайне проекты содержат терабайты текстур, звуков, 3D-моделей (`.fbx`, `.psd`, `.blend`), которые не поддаются текстовому диффу и дельта-сжатию.
   - В Git при клонировании репозитория скачивается **вся** история всех версий файлов, что привело бы к необходимости загружать сотен гигабайт или терабайт на каждый ПК (даже `git-lfs` не всегда решает проблему централизованной блокировки).
   - SVN изначально превосходно работает с бинарными файлами и позволяет скачивать только одну текущую версию.

2. **Эксклюзивная блокировка файлов (*File Locking / svn lock*):**
   - Бинарные ассеты невозможно автоматически смержить при конфликте. Если два геймдизайнера отредактируют одну текстуру или 3D-сцену, один из них потеряет работу.
   - SVN предоставляет встроенный надежный механизм пессимистической блокировки (`svn lock`), гарантирующий, что пока один разработчик редактирует файл, никто другой не может закоммитить изменения в него. В Git децентрализованная природа делает пессимистическую блокировку неэффективной.

3. **Гранулярный контроль доступа к подпапкам (Path-based / Directory-level Permissions):**
   - В финансовых структурах, банках, оборонных и госсекторах действуют жесткие политики безопасности: разработчик команды «А» должен иметь доступ только к подпапке `/trunk/module_a`, но не имеет права читать `/trunk/security_core`.
   - SVN на уровне сервера легко разграничивает права доступа на чтение и запись с точностью до конкретной папки или файла (`authz`).
   - В Git права доступа выдаются только на уровне всего репозитория целиком. Нельзя запретить склонировать отдельную папку внутри Git-репозитория.

4. **Частичный чекаут (Sparse / Shallow Checkouts без полной истории):**
   - В SVN можно сделать чекаут отдельной поддиректории: `svn checkout https://svn.repo/trunk/subproject`, не скачивая остальные гигабайты кодовой базы.
