## 3. Теоретическая справка

### 3.1. Почему нельзя работать напрямую в `main`?
Ветка `main` (или `master`) в современной парадигме DevOps представляет собой «священную корову» — эталонное состояние продакшен-кода. Любой коммит, попадающий в ветку `main`, потенциально готов к автоматическому тестированию, сборке артефактов и немедленному деплою на боевые сервера (Production).

Прямой коммит в ветку `main` категорически запрещен в командной разработке по следующим причинам:
1. **Высокий риск поломки сборки (Broken Build):** Непроверенный локальный коммит блокирует работу всей команды инженеров и останавливает CI/CD пайплайн.
2. **Невозможность изолированного отката (Rollback):** Если в `main` смешаны коммиты разных незавершенных функций, откат сбойной фичи невозможен без отката чужих полезных изменений.
3. **Утрата контекста и пропуск ревью:** Прямой коммит минует этап обязательного автоматического тестирования и коллегиального Code Review.

### 3.2. Концепция GitHub Flow
В отличие от тяжеловесной классической модели Git Flow (с длинноживущими ветками `develop`, `release`, `hotfix`), **GitHub Flow** представляет собой предельно простой, быстрый и эффективный цикл командной разработки:

```text
main        ──────────●───────────────●────── (стабильный продакшен)
             ╱                 ╱
feature-x   ──●──●──●──PR──●──● (ветка под конкретную задачу)
```

**Алгоритм GitHub Flow:**
1. Создание изолированной ветки от актуального `main` с информативным именем (`feature/add-auth`, `fix/login-bug`).
2. Локальная разработка и фиксация изменений серией атомарных коммитов по спецификации Conventional Commits.
3. Открытие Pull Request (PR) в ветку `main` для открытого обсуждения и запуска автоматических проверок CI.
4. Командное Code Review: коллеги анализируют дифф, оставляют комментарии и предложения по оптимизации.
5. Внесение исправлений новыми коммитами в ту же фича-ветку (PR обновляется автоматически).
6. Слияние изменений в `main` через **Squash and Merge** (для сохранения линейной, чистой истории коммитов).
7. Удаление выполненной фича-ветки на GitHub и локально.

### 3.3. Архитектурное сравнение Git и Subversion (SVN)

| Характеристика | Git (распределённая) | SVN (централизованная) |
| :--- | :--- | :--- |
| **Архитектура** | У каждого своя полная копия репозитория с историей | Один центральный сервер-хранилище |
| **Работа офлайн** | Полноценная (коммиты, ветки, слияния, просмотр логов) | Только локальные изменения файлов без возможности коммита |
| **Ветвление** | Мгновенно $O(1)$, легковесный указатель (41 байт) | Копирование директорий на сервере, медленно |
| **Скорость** | Очень высокая (локальный диск, хэш-деревья) | Зависит от сети и доступности сервера |
| **Слияние (Merge)** | Умное трехстороннее (3-way merge) с отслеживанием истории | Ручное, часто приводящее к tree conflicts |
| **Специализированная ниша** | Веб, микросервисы, облака, инфраструктура как код (IaC) | Монолиты с гигантскими бинарными ассетами (GameDev), пессимистическая блокировка файлов (`svn lock`), гранулярный доступ к подкаталогам |

### 3.4. Git в терминале (CLI) vs Git в IDE (VS Code)
- **Терминал (CLI):**
  - Полный контроль над низкоуровневыми операциями и внутренностями Git.
  - Возможность полной автоматизации через bash-скрипты, пайплайны CI/CD.
  - Работа на любых удаленных серверах, контейнерах и bastion-хостах по SSH без графической подсистемы.
- **IDE (VS Code, IntelliJ):**
  - Наглядная визуализация истории и посимвольного diff.
  - Удобный встроенный 3-way редактор конфликтов слияния.
  - Построчный blame (авторство строк и коммитов) в расширении GitLens.

### 4.4. Задание 4. Знакомство с SVN (демонстрационное)

Подготовлен аналитический документ `svn_comparison.md` с подробным разбором архитектурных вопросов:
1. **Почему ветвление в Git «дешевое», а в SVN «дорогое»?**
   В Git ветка — это легковесный 41-байтный указатель (хэш коммита). Создание занимает $O(1)$. В SVN ветка создается копированием директории внутри файловой системы репозитория (`svn copy`), требует обращения к серверу и сложного ручного разрешения конфликтов деревьев.
2. **Можно ли в SVN сделать коммит без интернета?**
   Нет, невозможно. Локально у клиента находится только рабочая копия (*Working Copy*). База истории и коммитов существует только на сервере, и коммит инкрементирует глобальный номер ревизии хранилища.
3. **В каких сценариях SVN предпочтительнее Git?**
   Монолиты с терабайтами тяжелых бинарных файлов (GameDev, CAD, 3D), необходимость жесткой эксклюзивной блокировки файлов (`svn lock`) и разграничение прав доступа на уровне отдельных подкаталогов (`authz`).

Файл закоммичен и отправлен в репозиторий:
```bash

git commit -m "docs: add SVN vs Git detailed comparison"
git push origin main
```

### 5.1. Теоретический блок: Сравнение Merge vs Rebase

**Вопрос:** *«В каком случае вы выберете rebase, а в каком — merge? Приведите пример.»*

**Ответ:**
1. **Выбор `rebase`:**
   - **Цель:** Получение абсолютно линейной, чистой истории коммитов без шумовых «Merge branch ...» коммитов.
   - **Механизм:** Git находит общего предка двух веток, временно сохраняет коммиты текущей ветки в виде патчей, переносит основу (base) ветки на вершину целевой ветки и поочередно накатывает коммиты. При этом каждый коммит пересоздается с новым SHA-хешем.
   - **Когда применять:**
     - Подтягивание актуальных изменений из `main` в свою персональную фича-ветку перед созданием Pull Request (`git pull --rebase origin main`).
     - «Причесывание» истории коммитов перед публичным ревью с помощью `git rebase -i` (склеивание мелких коммитов *wip*, удаление лишних, правка опечаток).
   - **Важно (Золотое правило Rebase):** Никогда не применять rebase к публичным веткам, с которыми работают другие разработчики!

2. **Выбор `merge`:**
   - **Цель:** Сохранение точной хронологии событий, контекста параллельной разработки и факта существования отдельной ветки.
   - **Механизм:** Создается трехсторонний коммит слияния (*3-way merge commit*), ссылающийся на двух родителей.
   - **Когда применять:**
     - Слияние протестированных фичей или релизных веток в `main` при классическом релизном цикле.
     - Объединение работы двух независимых команд, когда важно сохранить ветвление в графе истории.

## 6. Ответы на контрольные вопросы (для самопроверки)

### 1. Почему нельзя коммитить напрямую в `main`?
**Ответ:**  
Ветка `main` представляет собой стабильный продакшен-код, готовый к деплою. Прямые коммиты в `main` не проходят обязательный Code Review и CI/CD проверки, могут сломать рабочее окружение всей команде, затрудняют точечный откат сбойных фичей и разрушают версионную изоляцию.

### 2. Опишите шаги GitHub Flow своими словами.
**Ответ:**  
GitHub Flow состоит из 7 простых шагов:
1. Создание изолированной ветки от `main` под конкретную задачу.
2. Локальная разработка и фиксация изменений серией коммитов.
3. Открытие Pull Request в `main` для обсуждения.
4. Прохождение коллегиального Code Review.
5. Внесение исправлений новыми коммитами в эту же ветку.
6. Слияние изменений в `main` (Squash and Merge).
7. Удаление выполненной фича-ветки на сервере и локально.

### 3. Чем Pull Request отличается от простого merge?
**Ответ:**  
`Merge` — это низкоуровневая операция Git по соединению двух веток в единое дерево. `Pull Request` (PR) — это платформенный инструмент совместной работы GitHub/GitLab: он предоставляет веб-интерфейс для обсуждения кода, визуального просмотра diff, запуска автоматических проверок (CI/CD пайплайнов, тестов, линтеров), проведения ревью и выставления блокировок до получения одобрения коллег.

### 4. Что такое Code Review и зачем он нужен?
**Ответ:**  
Code Review — процесс взаимной проверки исходного кода коллегами перед включением его в основную ветку. Он нужен для выявления ошибок и архитектурных уязвимостей на ранней стадии, повышения качества и читаемости кода, выравнивания инженерных стандартов в команде и активного обмена опытом между разработчиками.

### 5. В чём принципиальная разница между Git и SVN?
**Ответ:**  
Принципиальная разница заключается в архитектуре: Git — распределенная VCS, где у каждого разработчика хранится полная независимая копия репозитория с историей, коммиты выполняются локально и дешево. SVN — централизованная VCS, где существует единый сервер-хранилище, клиенты держат только рабочую копию, а коммиты и ветвление требуют сетевого подключения и изменяют глобальное состояние сервера.

### 6. Что означает префикс `feat:` в сообщении коммита?
**Ответ:**  
Префикс `feat:` в соглашении Conventional Commits обозначает, что коммит добавляет в проект новую функциональность (*feature*) для пользователя. Это соглашение позволяет автоматическим скриптам формировать CHANGELOG.md и определять следующий номер версии по Semantic Versioning (SemVer: MINOR-версия).

### 7. Как отправить локальную ветку на GitHub впервые?
**Ответ:**  
С помощью команды с флагом отслеживания upstream: `git push -u origin <имя_ветки>` (или `git push --set-upstream origin <имя_ветки>`). Флаг `-u` связывает локальную ветку с веткой на удаленном репозитории, позволяя в дальнейшем использовать просто `git push` или `git pull`.

### 8. Почему DevOps-инженер обязан уметь работать с Git в терминале?
**Ответ:**  
В промышленной эксплуатации DevOps-инженер работает с серверами, bastion-хостами, CI/CD раннерами и контейнерами по SSH в headless-режиме (без графического интерфейса). Любые задачи автоматизации (bash-скрипты, GitLab CI, GitHub Actions) выполняются через CLI. Умение работать в терминале гарантирует полный контроль над сложными операциями Git (`rebase`, `cherry-pick`, `reflog`) в любой инфраструктурной среде.
